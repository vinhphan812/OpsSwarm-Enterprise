# S2 TaskGraph

**Contract version:** 1.0
**ADR references:** [ADR-006](../adr/ADR-006_SKILL_FRONTMATTER_CONTRACT.md) (frontmatter), [ADR-011](../adr/ADR-011_SKILL_ARTEFACT_CONTRACT.md) (artifact structure)
**Skill number:** 2 of 8
**Pipeline position:** Planning / diagnostic structuring

## Purpose

The S2 TaskGraph skill is the core intelligence component for structuring the automated investigation phase of an incident. It transforms the canonical IncidentContext received from S1 IntentGuard into a complex, executable Directed Acyclic Graph (DAG) of diagnostic tasks. This skill’s purpose is to break down the monolithic goal of "solving the incident" into a series of granular, actionable investigations that can be performed in parallel by different specialist profiles. By producing a well-structured DAG, it ensures logical flow — such as forcing observation tasks to complete _before_ invasive investigative ones — while optimizing resolution time through concurrent execution enablement.

## Inputs

This skill consumes the canonical IncidentContext generated by S1 IntentGuard.

- `IncidentContext`: (Service, Environment, Severity, Symptoms, CustomerImpact, Actor).
- `run_id`: (string) A unique identifier for the current incident execution, provided by the S8 OrchestrationHub to maintain state across execution passes.
- `HistoricalData`: (list of past runs, optional) Used to avoid redundant diagnostic steps.
- `TaskTemplateCatalog`: (dict) A configuration-driven catalog defining permissible task types for given services.

## Outputs

S2 TaskGraph produces a validated DAG of Task objects, where each task is clearly typed, scoped, and assigned.

- `Task[]`: A list of Task objects, where each contains:
     - `task_id` (string): Unique identifier.
     - `task_type` (enum: OBSERVE, INVESTIGATE, DIAGNOSE): Defines the nature of the task.
     - `depends_on` (list of task_ids): Defines task execution order within the DAG.
     - `assignee_profile` (string): Pre-assigned profile (e.g., infrastructure-investigator).
     - `parallelizable` (bool): Flag indicating if this task can run concurrently with others.
       This DAG is consumed directly by S4 RoleDispatch for execution.

## Key Rules & Constraints

1. Task Taxonomy: Tasks must strictly adhere to the OBSERVE, INVESTIGATE, DIAGNOSE taxonomy in that logical order.
2. Construction: The DAG must be strictly acyclic; circular dependencies raise an immediate build-time error in the S8 hub.
3. Parallelization: Tasks marked as OBSERVE are inherently parallelizable; DIAGNOSE tasks often have `depends_on` constraints on prerequisite OBSERVE/INVESTIGATE tasks.
4. Restart Policy: The skill MUST NOT prescribe "restart" or "revert service" as a default diagnostic or investigation task; these are destructive and fall under remediation.
5. Profile Alignment: Each task must be aligned to one of the canonical profiles: `observability-investigator`, `application-investigator`, `infrastructure-investigator`, or `database-investigator`.
6. Scope Enforcement: Tasks must only access the services identified in the `IncidentContext`.
7. Determinism: Building the DAG for the same `IncidentContext` must produce the same task structure every time.

## Error Codes

| Code      | Name                              | Trigger                                                | Resolution                                              |
| --------- | --------------------------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| `S2-E001` | `INVALID_DAG_CONFIGURATION_ERROR` | `IncidentContext.service` not in `TaskTemplateCatalog` | Halt; flag incident; request manual intervention        |
| `S2-E002` | `CYCLE_DETECTED`                  | Circular dependency detected in DAG                    | Immediate build-time error; S8 hub notified             |
| `S2-E003` | `DAG_COMPLEXITY_EXCEEDED`         | Calculated DAG exceeds 50 tasks                        | Trigger security gate requiring human authorization     |
| `S2-E004` | `AMBIGUOUS_SERVICE_MAP`           | Service maps to no known task template                 | Halt; post request to GitHub issue thread               |
| `S2-E005` | `MISSING_TASK_ASSIGNEE`           | Task has no matching profile in CapabilityCatalog      | Flag; halt dispatch until resolved                      |
| `S2-W001` | `HIGH_SEVERITY_INJECTION`         | sev:1 incident; redundant tasks auto-injected          | Informational; pipeline continues                       |
| `S2-W002` | `INSUFFICIENT_EVIDENCE`           | Symptoms empty or insufficient                         | Initialize placeholder `OBSERVE` task for log gathering |

## Edge Cases

- Ambiguous Services: If the `IncidentContext.service` is not in the `TaskTemplateCatalog`, the skill immediately halts and flags the incident as `INVALID_DAG_CONFIGURATION_ERROR`.
- High-Severity Incidents (sev:1): The skill is programmed to automatically inject additional redundant diagnostic tasks to ensure comprehensive coverage.
- Missing Evidence: If input `Symptoms` are empty or insufficient, the skill initializes with a placeholder `OBSERVE` task dedicated solely to gathering logs before proceeding.
- DAG Complexity: If the calculated DAG exceeds 50 tasks, it triggers a security gate requiring human authorization to ensure the response isn't causing resource exhaustion.

## Interactions

- Upstream: S1 IntentGuard (consumes the input `IncidentContext`).
- Downstream: S4 RoleDispatch (consumes the DAG for task execution).
- S8 OrchestrationHub: Provides the `run_id` and manages the high-level execution state of the graph.
- Human/External: If the expert system cannot formulate a valid DAG due to excessive complexity or ambiguity, it posts a request to the GitHub issue thread, asking for expert manual intervention.

## Best Practices

- **Template completeness:** Keep the `TaskTemplateCatalog` comprehensive and up-to-date. If a service is added to the system without a corresponding template entry, S2 will halt every incident for that service with `S2-E004`.
- **DAG simplicity:** Prefer shallow, wide DAGs over deep, narrow ones. Deep DAGs (many serial `depends_on` chains) increase the blast radius of a single failed task. Target a depth of 3-4 levels maximum.
- **OBSERVE task design:** Every DAG should begin with at least one `OBSERVE` task that establishes baseline system state. This guards against the `S2-W002` (insufficient evidence) path.
- **Parallelization hints:** Mark tasks as `parallelizable=True` only when they have no shared resource dependencies. Incorrect hints cause resource contention; conservative `False` is always safe.
- **High-severity planning:** For `sev:1` incidents, explicitly review the auto-injected redundant tasks (log `S2-W001`) to ensure they do not conflict with each other.
